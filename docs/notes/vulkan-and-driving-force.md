# Vulkan + driving-force dropdown (2026-08-24)

Two additions shipped together (build clean, service restarted, plumbing verified end-to-end up to the model call).

## Vulkan — the coding specialist
Cloned from Atlas in `container/agent-runner/src/index.ts` (`SUBAGENTS` entry, `vulkan-core` toolset in `toolsets.ts`). Async background agent like Atlas; both share one `backgroundJobs` map + `spawnBackgroundJob(delegate, …)` (renamed from the atlas-only `spawnAtlasBackgroundJob`). Atlas keeps Bash + desktop/app control; Vulkan owns code-editing (`vulkan-core` = Read/Write/Edit/Glob/Grep + Bash, which atlas-core lacks) + builds/tests + heavy scripting — no browser, no desktop, no screenshot, no `open_app`, so it edits code and reports done; seeing the result is Atlas's job, routed by the orchestrator. Both inherit the `data/skills/` library via the same skill-merge. `maxIterations: 200`. Vulkan has its **own model dropdown** (`vulkanModel` router_state → `VULKAN_MODEL`, falls back to orchestrator) — intended for a frontier cloud model, NOT the shared Toolcall model. `spawnBackgroundJob` selects `VULKAN_MODEL` for vulkan, `ATLAS_MODEL` for atlas. Orchestrator routing: roster bullet, "when in doubt → atlas except coding → vulkan", a coding cue word, and the PII-local line now covers both cloud agents.

Vulkan is also the **churn-escalation target**: when an atlas job is watchdog-aborted for read-only-call churn (still `CHURN_ABORT_AFTER` research calls after the commit nudge), the watchdog auto-spawns vulkan on the same task via `spawnBackgroundJob('vulkan', j.task, …)`, records `j.escalatedTo`, and consumes the one retry credit (`taskSig`) so the orchestrator does not double-dispatch. Vulkan is exempt from the one-atlas-at-a-time gate — the watchdog deliberately spawns it while atlas is winding down.

## Driving force — orchestrator preamble dropdown
`data/driving-forces/*.md` presets replace the orchestrator's `# ROLE` preamble; the roster + routing core stays fixed (swap HOW it thinks, not WHO it delegates to). Empty id = "Warden (default)" = the in-code `DEFAULT_PREAMBLE` (preserves the dynamic `assistantName`). Settings GET returns `drivingForce` + `drivingForces` (read from the dir, label = first H1); no separate list endpoint. Switching the driving force clears context: `status-server` sets `orchestrator:context_clear_at` + advances `last_agent_timestamp`; the host's `buildPrompt` gates `<chat_history>` on that marker; the agent-runner's `buildSystemPrompt()` reads the preset file and the `_clearContextRequested` flag (set on a changed `contextClearAt` via `applySettingsSync`) resets the in-memory `messages` to a fresh system prompt at the top of the orchestrator loop — which also finally wires up the previously-dead `clear_context` tool. Note: a router-state save respawns the agent-runner child (`restart:true`), so the driving-force change is usually picked up by a fresh child; the in-loop clear is the belt-and-suspenders for non-restart cases.

Presets: staff-engineer, first-principles, paranoid-reviewer, ship-it, architect, debugger, socratic, mentor.
