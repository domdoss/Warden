# Plan v2: Two-tier security — Sentry (data) → Heimdall (vision) → alert

## Topology
- **Laptop (eyes/ears):** runs `python main.py` (RF-DETR + structured situation tracker + voice client). It publishes frames on its own `/frame` HTTP server and POSTs `AWARENESS` JSON events to the desktop Warden.
- **Desktop (brain):** runs the Warden service, Sentry on a light local model, and Heimdall on a vision-capable local model. It receives awareness JSON, lets Sentry decide, escalates to Heimdall for vision confirmation, and posts alerts (with image) to the chat so Telegram shows them.

## What changes

### 1. Python app (laptop)
- Keep the structured situation tracker from Plan v1.
- Keep `/frame` server, but make its bind host configurable so the desktop can reach it (already in `settings.yaml`).
- Remove all disk frame saving and the armed security path.
- When `/alert/open` arrives from the desktop, set a red-button state in the GUI; keep it simple — no review window needed.
- Default `warden.base_url` points at desktop; `frame_server.host` defaults to `0.0.0.0` so desktop can pull frames.

### 2. Sentry prompt file (`security/sentry.md`)
- Loaded as the Sentry sub-agent system prompt.
- Contains the "normal/allowed" rules the user edits: who is allowed to be where, when the user is away, what counts as suspicious.
- Sentry receives only the JSON data (no image), decides whether the situation is normal or anomalous.
- If anomalous, Sentry calls a new tool `escalate_to_heimdall(reason, data_snapshot)`.
- If normal/greeting-worthy, Sentry can `send_message` a greeting and record `awareness_log`.

### 3. Sentry model setting in dashboard
- Add a `Sentry` model dropdown in the dashboard Models card.
- Persist as router state `sentry:model`.
- Pass to the Sentry sub-agent as `containerInput.model`.
- Update `resolveAwarenessModel()` to read `sentry:model` instead of `heimdall:model`.

### 4. New tool: `escalate_to_heimdall`
- Registered in `awareness-tools.ts` (toolset `awareness`).
- Calls a new host callback `escalate_to_heimdall`.
- The host callback spawns Heimdall with:
  - The current local time.
  - The AWARENESS JSON data.
  - A fresh live frame pulled from the laptop `/frame` server.
  - Instructions to confirm/deny the anomaly and, if confirmed, alert the user.

### 5. Heimdall flow (desktop)
- Heimdall sub-agent receives the data + live image.
- System prompt (baked in code): "You are Heimdall. Given the detector data and a live frame, confirm or deny that the described anomaly is actually happening. If you confirm, send_message the user with a concise alert and append the image reference so it shows in Telegram, then call open_security_alert to light the red button on the laptop. If you deny, record security_log as normal and stop silently."
- Heimdall uses `webcam_capture` or a new `security_frame` host callback to get the live frame from the laptop. The frame is saved to the desktop's `groups/owner/attachments` and referenced as `[Image: attachments/<file>.jpg]`.
- Heimdall calls `open_security_alert` which POSTs `/alert/open` to the laptop.

### 6. Warden host routing (`src/index.ts`)
- `AWARENESS` messages still route to Sentry (fire-and-forget), but Sentry now may call `escalate_to_heimdall`.
- Remove the old `SECURITY ALERT` image pipe (no more JPEG alerts from Python).
- Add host callback `escalate_to_heimdall(args)` that:
  - Pulls frame from the configured laptop `/frame` URL.
  - Saves it to `groups/owner/attachments`.
  - Spawns Heimdall sub-agent with the data + image.
- Keep `open_security_alert`, `close_security_alert` callbacks pointing at the laptop IP (configurable via dashboard/router state, no hardcoded defaults).
- Add `sentry:model` to `/api/settings` read/write and status endpoint.

### 7. Dashboard UI (`public/js/app.js` + `src/status-server.ts`)
- Add `Sentry model` dropdown in the Models card.
- Add general settings fields for:
  - `securityLaptopIp` (or `securityFrameUrl` + `securityControlUrl`)
  - Optionally `sentry:model` in the same Models save call.

### 8. Security log
- Heimdall records `security_log` on confirm/deny.
- Sentry records `awareness_log` on every event.
