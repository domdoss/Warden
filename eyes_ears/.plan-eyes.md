# Plan: Live structured-awareness stream from the security detector

## Goal
Shift the Python security detector from "send a JPEG and let a vision agent look at it" to "maintain a local structured situation model and send compact JSON change events to Warden." The orchestrator / Sentry can then build a map of what is happening and decide whether to act.

## Current state
- `main.py` already has a basic awareness tracker: it posts `AWARENESS — arrival/departure` JSON messages to Warden.
- Warden host routes any message starting with `AWARENESS` directly to Sentry (background granite-based agent), bypassing the orchestrator.
- The security alert path (armed → Heimdall review → red button) still sends JPEG frames.

## Proposed changes

### 1. New module: `core/situation.py`
A small stateful tracker that builds a structured "situation" each frame:
- `timestamp`, `frame_size`
- `persons`: list of tracked persons with stable IDs, bbox center, size, confidence, keypoints
- `motion`: area, ratio, bounding box of motion region
- `camera`: `covered` (bool), `moved` (bool, detected by frame-to-frame pHash shift)
- `objects`: other COCO detections in frame (chair, laptop, phone, etc.)
- `room`: occupied / empty, seconds in current state

Person tracking uses simple center-based IOU to keep IDs stable across frames. The tracker detects:
- `arrival` — new person ID appears
- `departure` — person ID gone for > N frames
- `entered_object` / `movement` — significant bbox/center shift of a tracked person
- `camera_covered` / `camera_uncovered`
- `camera_moved` — scene changed abruptly (someone moved the camera / door opened)
- `motion_burst` — large motion area spike while room empty

### 2. Update `core/warden.py`
- Keep `send_awareness(event, data)`; extend the payload so the orchestrator can also use it.
- Add a richer `send_situation(situation_dict)` that posts `AWARENESS — situation at <ts>. data: <json>`.

### 3. Update `main.py`
- Replace the simple arrival/departure block with calls to the new `SituationTracker`.
- On every frame: update tracker, get a `change_event` (or None).
- If a change event fires and the cooldown permits, call `warden.send_awareness(event, data)`.
- Keep the armed security path as-is: when armed and a person/covered camera is present, still send one frame to Heimdall for abnormal/normal judgment. This is a separate concern from awareness.
- Stop saving raw/annotated awareness frames to disk. Only save frames for actual security alerts (or make it configurable, default off).

### 4. Config additions in `settings.example.yaml`
```yaml
awareness:
  enabled: true
  cooldown_seconds: 30          # min seconds between any awareness posts
  presence_debounce: 3          # consecutive frames before arrival/departure
  empty_threshold_seconds: 30   # only announce arrival if room was empty this long
  motion_min_area: 500          # motion area that counts as movement
  camera_moved_threshold: 12    # pHash Hamming distance threshold
  object_classes: []            # if empty, track all COCO classes; else only listed
```

### 5. Warden-side routing question
Currently `AWARENESS` messages are consumed by Sentry and never reach the orchestrator. To let the orchestrator "choose to do something," we have two options:
- **Option A (minimal):** Keep routing to Sentry only. Sentry can `send_message` if it decides the user should know; otherwise it stays silent. The orchestrator sees the chat message if Sentry speaks.
- **Option B (orchestrator-visible):** Also expose the latest situation via a new host tool/endpoint (e.g. `get_situation` callback, or store it in router state). The orchestrator can query it on demand, or awareness messages can be copied into the orchestrator's context.

## Open questions for approval
1. **Recipient:** Should the orchestrator see the raw awareness JSON directly, or only via Sentry's spoken summaries? (A vs B above.)
2. **Security alerts:** Keep the existing armed Heimdall image-review path, or also convert it to structured data + a different escalation flow?
3. **Disk writes:** Turn off all awareness frame saving, or keep it as an opt-in debug feature?
4. **Camera-moved detection:** Is pHash frame-to-frame comparison acceptable, or do you want optical-flow / feature-based detection?
5. **Person re-identification:** Simple IOU tracking is fine for one camera, but IDs reset on occlusion. Good enough for now?

## Scope of this plan
Implement the Python-side structured stream first (`core/situation.py` + `main.py` wiring). Leave Warden-side routing as-is (Option A) unless you choose Option B.
